# 지금 다루는 코드베이스가 무엇인가

> 상태: 작성완료
> 준수 강도: 필수
> 최종갱신: 2026-10-01
> 출처: 우리가 쓴 것. superpowers 파생 아님

**「시스템」은 작업 단위 하나다** — 저장소 하나일 수도, 한 솔루션 안의
프로젝트 묶음일 수도 있다. 시스템 하나에 소스 경로와 따라야 할
기술 스택 지침(`techbase`)이 붙는다.

이것이 정해지지 않으면 **어떤 지침을 읽을지도, 산출물을 어디에 쓸지도 모른다.**
그래서 하네스는 여기서 먼저 멈춘다.

## 시스템 확정

세션 시작 훅이 둘 중 하나로 정한다. **추측하지 않는다.**

```
런처로 들어옴    vReins.exe 가 VREINS_* 환경변수를 채워 준다
직접 들어옴      지금 폴더를 시스템 정의의 「경로」와 대조해 알아낸다
둘 다 아님       모른다고 보고한다
```

두 번째가 추측이 아닌 이유 — **커밋된 정본과 비교하기 때문이다.** 이름으로
폴더를 맞히려던 옛 방식은 ABCD 에서 틀린 폴더를 골랐고, 그래서 버렸다.

훅이 「확정 근거」를 같이 낸다. 그게 틀렸으면 그 자리에서 알 수 있다.

## 시스템 정의 파일

```
systems\{시스템유형}\{시스템코드}.json
```

**시스템유형과 시스템코드를 파일 안에 적지 않는다.** 파일이 놓인 자리가 그것이다.
같은 것을 두 번 적으면 어긋날 자리가 생긴다.

```json
{
  "시스템명": "A공정 B라인",
  "systemBase": ["Acme_Level2_UI", "Acme_Level2_TASK"],
  "형상관리": "TFS",
  "경로": {
    "frontend": "C:\\{형상관리루트}\\{솔루션}\\{시스템폴더}",
    "backend":  "C:\\{형상관리루트}\\{솔루션}\\{시스템폴더}_TASK",
    "logs":     "\\\\{로그서버}\\Log"
  },
  "db": "postgresql://{호스트}:{포트}/{DB명}"
}
```

`db` 에 **계정과 비밀번호를 적지 않는다.** 주소는 여기, 계정은 `{루트}\config\` 에
두고 런처가 실행 순간에 합친다. 저장소 어디에도 비밀번호가 없는 이유다.

**호스트와 포트는 여기 적는다.** `config\` 에 있는 것은 계정과 비밀번호뿐이다.

갈라 둔 이유는 **읽는 쪽이 다르기 때문이다.** 이 파일은 작업 중에 읽고, 읽은 것은
산출물에 인용된다 — 계정이 여기 있으면 문서에 남는다. `config\` 는 런처만 읽는다.
둘 다 커밋되지 않고 내 PC 에만 있다.

**경로는 실물을 가리킨다.** LEVEL2 는 `Acme_Level2_UI\` 와 `_TASK\` 밑에
같은 이름 폴더가 있는데 **파일 0개인 빈 껍데기**다. 실물은 평면 루트
`Acme_Level2\` 에 있다 — **폴더가 있다고 소스가 있는 게 아니다.**

## 한 층

```
{루트}\systems\{유형}\{코드}.json     내 PC. 런처 [프로젝트 추가]·[프로젝트 설정] 이 쓴다
```

**플러그인에는 없다.** 2026-09-22 회의로 시스템 정보는 플러그인에 넣지 않는다 —
깃허브 공개 배포본이고, 소스 경로는 PC 마다 다르다. 한때 「플러그인이 팀 공통,
루트가 내 것」 두 층이었는데 플러그인 층은 언제나 비어 있었다. 비어 있는 층을
문서에 남기면 「팀 공통에 올리면 된다」는 **없는 길**을 가리키게 된다.

세션 시작 훅이 이 파일을 읽어 **시스템명 · 기술기반 · 형상관리 · 소스 경로**를 낸다.
런처로 들어와도 낸다 — 환경변수에는 경로가 없어서, 이것이 없으면 모델이 소스 자리를 추측한다.

## 담당 판정

```
소스 프로그램이 로컬에 있다  =  최신 버전을 받았다  =  내가 맡은 시스템
```

담당 목록을 따로 적지 않는다 — **목록은 낡지만 폴더는 낡지 않는다.**
적어 놓고 Get Latest 를 안 하면 목록에는 있는데 못 여는 상태가 되고,
그것을 사람이 눈치채기 어렵다.

`logs` 는 세지 않는다. **로그 공유폴더는 담당이 아니어도 열린다.**

## 기술기반 추출

```
"frontend": "C:\{형상관리루트}\Acme_Level2_UI\{시스템폴더}"
                          └─────────┬─────────┘
                          여기서 systemBase 를 뽑는다
```

사람에게 따로 묻지 않는다. 경로 키를 역할 이름(프론트엔드·백엔드)으로 붙여도
**경로 안의 폴더명**에서 읽으므로 `wiki\{유형}\COMMON\_manual\{기술기반}-*.md` 과 묶인다.

기술기반 폴더가 경로에 없으면 `systemBase` 는 빈 채로 남는다 —
**읽을 지침이 없다는 뜻이고, 그게 맞는 값이다.**

## 레지스트리는 없다

한때 `systems.md` 한 장에 시스템 목록 · 시스템명 · 기술기반 · 모듈 코드 조회표를 두고
세션마다 「이 시스템 행」을 넣었다. 2026-10-01 에 없앴다 — 그 행이 주던 것이 **전부 이미
다른 데 있었다.**

```
시스템명 · 기술기반 · 형상관리 · 소스 경로     시스템 정의 JSON  (이 문서)
설명 · 소유자 · 관계                        {코드}-OVERVIEW.md 머리말
팀이 아는 시스템 목록                        ls {위키}\{유형}\   — 폴더가 목록이다
```

같은 것을 세 벌 적으면 둘은 반드시 낡는다. 실제로 레지스트리 파일은 끝내 어디에도
만들어지지 않았고, 세션마다 「못 찾았다」만 찍혔다.

둘은 답하는 질문이 다르다 — 시스템 정의는 「**이 PC 에서** 진입할 수 있는 것」,
위키 폴더는 「팀이 아는 것 · 산출물이 쌓이는 곳」. 위키에 있는데 정의가 없으면 내가
안 맡은 시스템일 뿐이고, 정의가 있는데 위키에 없으면 위키에 자리를 만든다.
`lint.py` 가 둘을 대조한다.

## 신규 등록

맡게 된 시스템이 없으면 **기다리지 않는다.**

```
런처의 [프로젝트 추가]                화면으로 등록
{루트}\systems\ 에 json 을 쓴다      손으로 등록. README.txt 에 견본이 있다
```

만든 파일은 `{루트}\systems\` 에 남고 **나만 쓴다.** 위키에 그 시스템 폴더
(`{유형}\{코드}\{코드}-OVERVIEW.md`)가 없으면 `_sample\` 을 베껴 같이 만든다 —
그래야 산출물이 갈 자리가 생긴다.
