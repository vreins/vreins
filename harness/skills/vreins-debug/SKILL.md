# 고치기 전에 원인을 찾는다

> 상태: 작성완료
> 준수 강도: 필수
> 최종갱신: 2026-09-21
> 출처: obra/superpowers 의 `systematic-debugging` 파생 (MIT · Jesse Vincent)
>       → `harness\LICENSE` · `harness\ATTRIBUTION.md`

## 한 줄

**증상을 고치는 것은 실패다.** 원인을 찾기 전에 고치면 시간을 버리고 새 버그를 만든다.

## 철칙

```
원인 조사를 끝내기 전에는 수정안을 내지 않는다
```

1단계를 안 끝냈으면 고칠 방법을 말할 수 없다.

## 특히 지켜야 할 때

```
급할 때            급하면 찍고 싶어진다. 체계적인 쪽이 결국 더 빠르다
「딱 하나만 고치면 될 것 같다」   그 생각이 들면 아직 원인을 모르는 것이다
이미 두 번 고쳐 봤을 때
앞의 수정이 안 먹혔을 때
```

**쉬워 보여도 건너뛰지 않는다.** 쉬운 버그에도 원인은 있다.

---

## 1단계 — 원인 조사

**어떤 수정도 시작하기 전에.**

### 오류 메시지

스택트레이스를 통째로 읽는다. 줄 번호 · 파일 경로 · 오류 코드를 적어 둔다.
**답이 거기 적혀 있는 경우가 많다.**

### 재현

```
어떤 조건에서 나나 · 매번 나나 · 특정 데이터에서만 나나
```

재현이 안 되면 **추측하지 말고 자료를 더 모은다.**

### 최근 변경

```
TFS   변경 집합(changeset) 이력 · 누가 언제 무엇을
git   git log · git diff
그 외  설정 파일 · DB 스키마 · 상대 시스템의 전문 포맷
```

### 여러 프로세스에 걸친 경우

우리 환경이 대부분 이렇다. **설비(L1) → 수신관리 → 편집 → DB → MES(L3)** 처럼
프로세스가 여럿이고 각각 따로 돈다.

**고치기 전에 경계마다 증거를 남긴다.**

```
각 경계에서
  무엇이 들어왔나 · 무엇이 나갔나 · 값이 언제 달라졌나

한 번 돌려서 「어디서」 깨지는지 확인한다
그다음에 그 프로세스 하나만 파고든다
```

로그가 이미 있으면 그것부터 본다 — `I/F Log 관리` 태스크가 전문을 남기고,
로그 공유폴더에 프로세스별 파일이 쌓인다. **없는 로그를 새로 넣기 전에
있는 로그를 다 봤는지 확인한다.**

### 값을 거슬러 올라가기

```
나쁜 값이 어디서 처음 생겼나
그 값을 누가 넘겼나
그 위는
```

**끝까지 올라가서 거기를 고친다.** 중간에서 막으면 다른 경로로 또 나온다.

---

## 2단계 — 비교

```
1  비슷한데 잘 되는 것을 찾는다      같은 솔루션의 다른 시스템 · 다른 태스크
2  그 코드를 끝까지 읽는다           훑지 않는다. 부분만 알면 반드시 틀린다
3  다른 점을 전부 적는다             「이건 상관없겠지」를 하지 않는다
4  무엇에 의존하는지 본다            설정 · 참조 · 상대 시스템 · 순서
```

**우리 환경에서 특히 잘 통한다.** 시스템이 여럿이고 구조가 같아서,
ABCF 에서 되는 것이 ABCD 에서 안 되면 **차이가 곧 답이다.**

---

## 3단계 — 가설 하나, 최소 시험

```
1  가설을 한 문장으로 적는다        "X 때문이다. 근거는 Y"
2  가장 작게 바꿔 시험한다          한 번에 하나만
3  결과를 본다
     맞았다   → 4단계
     틀렸다   → 새 가설. 앞의 수정 위에 더 얹지 않는다
```

**모르면 모른다고 말한다.** 아는 척하지 않고 묻는다.

---

## 4단계 — 수정

```
1  재현 절차를 먼저 적는다          고치기 전에. 고친 뒤에는 재현이 안 된다
2  한 가지만 고친다                 「온 김에」 하지 않는다
3  확인한다                        원래 증상이 사라졌나 · 다른 것이 깨지지 않았나
```

**재현 절차가 테스트를 대신한다.** 우리 환경에는 테스트 프로젝트가 없다 —
그러니 「어떤 조건에서 어떻게 확인했나」를 글로 남기는 것이 그 자리다.
`05-testing-{제목}.md` 에 그대로 들어간다.

### 세 번 실패하면

```
1~2회 실패   1단계로 돌아간다. 새로 안 것을 가지고 다시 본다
3회 이상     구조를 의심한다. 네 번째 수정을 시도하지 않는다
```

**이런 모양이면 구조 문제다.**

- 고칠 때마다 **다른 자리**에서 새 문제가 나온다
- 고치려면 「대대적으로 손봐야」 한다
- 하나 고치면 다른 데가 깨진다

가설이 틀린 게 아니라 **구조가 틀린 것**이다. 더 고치기 전에 사람과 의논한다.

---

## 멈춰야 하는 신호

이런 생각이 들면 **1단계로 돌아간다.**

- 「일단 급한 불부터 끄고 나중에 보자」
- 「X 를 바꿔 보고 되는지 보자」
- 「여러 개 한꺼번에 바꾸고 돌려 보자」
- 「확인은 나중에 하고 일단 고치자」
- 「아마 X 일 거다」
- 「완전히는 모르겠지만 이렇게 하면 될 것 같다」
- 원인을 안 밝히고 고칠 것 목록부터 나열하고 있다
- **이미 두 번 고쳤는데 「한 번만 더」**

## 빠져나갈 구멍

| 하고 싶은 말 | 실제 |
|---|---|
| 「간단한 거라 절차가 필요 없다」 | 간단한 버그에도 원인은 있다. 절차는 간단할수록 빨리 끝난다 |
| 「급해서 시간이 없다」 | 찍어 보는 것보다 체계적인 쪽이 빠르다 |
| 「일단 고치고 조사는 나중에」 | 첫 수정이 방향을 정한다 |
| 「여러 개 같이 고치면 빠르다」 | 무엇이 들었는지 못 가린다. 새 버그가 생긴다 |
| 「참고 코드가 길어서 적당히 봤다」 | 부분만 알면 반드시 틀린다 |
| 「원인이 보인다, 고치겠다」 | 증상을 본 것과 원인을 아는 것은 다르다 |
| 「한 번만 더 고쳐 보자」 (2회 실패 후) | 3회 실패는 구조 문제다. 또 고치지 말고 의심해라 |

## 원인이 정말 없을 때

환경·타이밍·상대 시스템 문제로 밝혀지면 그것도 결론이다.

```
1  무엇을 조사했는지 적는다
2  대응을 넣는다            재시도 · 타임아웃 · 오류 메시지
3  다음을 위한 로그를 남긴다
```

**다만 「원인 없음」의 대부분은 조사가 덜 끝난 것이다.**

## 절차와의 연결

```
트러블슈팅 트랙   01-troubleshooting-{제목}.md 한 장. 이 스킬의 4단계가 그 뼈대다
표준 트랙        02-analysis-{제목}.md 의 「현재 동작」을 채울 때 1~2단계를 쓴다
끝났다고 말할 때  vreins-verify 스킬로 넘어간다
```
