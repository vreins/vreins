# 시스템 개요 (overview.md)

> 상태: 작성완료
> 준수 강도: 권장 — 목차 구조는 필수, 표현은 자유
> 최종갱신: 2026-09-21

`wiki\{시스템유형}\{시스템코드}\overview.md` 를 이 목차대로 쓴다.

**이 문서가 절 구성의 정본이다.** 위키는 절 목록을 갖지 않는다 — 한때 양쪽에 있었고,
위키 쪽이 5절로 굳은 채 실물과 하네스는 7절로 자랐다. 훅 주입문과 스킬이 전부 절 번호로
참조하는데 **모든 `overview.md` 가 틀린 목록을 규약이라고 가리키고 있었다.**
두 벌이면 한쪽이 낡고, 낡은 쪽이 더 오래 간다.

---

## 용도

**그 시스템 하나의 현재 모습.** 사실이지 지침이 아니다.

    techbase\{기술기반}\    규칙.   어긋나면 이쪽이 이긴다
    wiki\…\overview.md      배경.   규칙을 덮지 못한다

읽는 순서에서 **3번**이다. 1번(레지스트리)과 2번(techbase)이 「무엇을 지킬 것인가」를
정한 뒤, 이 문서가 「여기는 어떤 곳인가」를 준다. 그래서 여기 적은 것이 지침과 충돌하면
**지침이 이긴다.** 충돌한다는 사실 자체는 5절에 적는다.

## 머리말

```yaml
---
type: overview
system: ABCD
lifecycle: production
description: A공정(사업장1). ABCD####와 ABCF####는 번호가 같아도 뜻이 다른 것이 섞여 있다
owner: A공정담당
techbase: [Acme_ERP_MES_V6]
related:
  - system: ABCF
    rel: 번호충돌
    why: 번호가 같아도 뜻이 다른 것이 섞여 있다
    n: 12
    observed: 2026-09-21
    source: 우리 DB 주석 실측
updated: 2026-09-21
---
```

**각 칸이 왜 있는지.** `type`·`system`·`updated` 를 뺀 넷이 2026-09-21 에 늘었고,
`status` 가 그때 빠졌다.

| 칸 | 값 | 왜 있나 |
|---|---|---|
| `lifecycle` | `skeleton` · `production` · `deprecated` | 옛 `status` 자리다. **`status` 는 47/47 이 같은 값이라 정보가 0이었다** — 「작성완료/부분작성」은 절마다 다른데 파일 하나에 값 하나를 붙이면 언제나 거짓말이 된다 |
| `description` | 한 줄 | **`index.md` 가 그대로 긁어 간다.** 없으면 목차 줄이 비고 사람이 목차에서 그 시스템을 고를 수 없다 |
| `owner` | 역할명 **한 덩어리** — `A공정담당` | **사람 이름은 안 적는다. 사람은 바뀌고 역할은 안 바뀐다.** 누가 그 역할인지는 레지스트리 한 곳에 적는다 — 48곳에 흩어 놓지 않는다 |
| `related` | 아래 여섯 키 | 다른 시스템과 엮이는 위험. **`index.md` 의 「공정을 가로지르는 위험」 표를 기계가 여기서 모은다.** 한쪽만 적어도 반대쪽이 그 표에 뜬다 |
| `techbase` | `[Acme_ERP_MES_V6]` | **`techbase\` 폴더명 그대로.** 값이 곧 경로다 — `acme-mes-v6` 처럼 줄여 쓰면 폴더를 못 찾는다. 그 폴더가 어디 있는지는 `vreins-rules` 3절 |

`related` 의 키는 여섯이다.

    system    상대 시스템코드
    rel       넷 중 하나 — 번호충돌 · 모듈사본 · 층구분 · 기능중복
    why       한 줄. 무엇이 위험한가
    n         셀 수 있으면 개수
    observed  언제 확인했나
    source    무엇을 보고 알았나

**`status` 를 쓰지 않는다.** 남아 있으면 지운다.

`techbase` 는 **레지스트리와 같아야 한다.** 다르면 4절에 다른 이유를 적는다.
비어 있는 시스템(1:1 이라 공유할 지침이 없는 경우)은 빈 배열로 두고,
본문 맨 위에 그 사실을 한 줄로 올린다.

    ## ⚠ 이 시스템은 techbase 가 없다

H1 은 시스템코드 하나다. 그 아래 한 줄로 정본 포인터를 남긴다.

## 절 구성

```
1. 이 공정이 무엇인가          현장에서 무슨 일이 일어나는가. 시스템이 아니라 공정
2. 공정 흐름                   앞뒤로 무엇과 붙는가. 상류·하류
3. 화면·태스크 구성            실물 목록. 정본은 소스이고 여기는 요약이다
4. 담당 범위                   저장소 · techbase · 형상관리 · DB · 서버 경로 · 소유자
5. techbase 지침과 다른 예외    없으면 「없음」 한 줄. 빈 절로 두지 않는다
6. 이 시스템만의 함정          실측으로 나온 것만. 지어내지 않는다
7. 관련 이력                   작업 폴더로 가는 표
```

### 1 · 2절 공정

「무슨 화면이 있다」가 아니라 **「무엇을 만드는 공정인가」**다. 화면은 3절이 갖는다.
이 둘이 비면 나머지가 다 있어도 처음 온 사람은 아무것도 모른다.

대개 **소스에서 안 나온다.** 담당자에게 물어야 채워지므로, 모르면 아래 형식을 쓴다.

    <!-- UNWRITTEN -->

    **누구에게 물어야 채워지나** — {누구}. {무엇을 먼저 물어야 하는지}

**「누구에게 물어야 채워지나」를 같이 적는 것이 이 표식의 핵심이다.**
빈 절은 언젠가 채워지지 않는다. 채울 사람이 적혀 있어야 채워진다.

### 3절 정본

실물(TFS 프로젝트 · 화면 목록)이 정본이고 여기는 **읽을 수 있게 묶어 둔 것**이다.
전수 나열이 목적이 아니다. 묶음으로 갈라 표로 적고, 개수와 실물 경로를 같이 남긴다.

세는 값(프로젝트 수 · 화면 수)은 **언제 센 것인지 알 수 있게** 4절 `updated` 와 묶인다.
소스가 자라면 이 절은 반드시 낡는다 — 낡는 것이 정상이고, 그래서 정본이 아니다.

### 4절 담당 범위

| 항목 | 값 |
|---|---|
| 저장소 | |
| techbase | 레지스트리와 같은지 밝힌다 |
| 형상관리 | TFS · git · svn · 없음 |
| DB | |
| 서버 경로 | |
| 소유자 | |

모르는 칸은 비우지 말고 `<!-- UNWRITTEN -->` 와 **모르는 이유**를 적는다.
「권한 밖이라 못 본다」와 「아직 안 물어봤다」는 다음에 할 일이 다르다.

### 5절 예외

예외가 없으면 **「없음」 한 줄을 적는다.** 비워 두면 「예외가 없다」와
「아직 안 봤다」가 구분되지 않는다.

### 6절 — 실측만

**지어내지 않는다.** 함정은 겪어야 나오는 것이고, 그럴듯한 추측을 적어 두면
다음 사람이 그것을 사실로 읽는다. 아직 없으면 없다고 적는다.

추측을 적고 싶으면 **추측이라고 적는다** — 「확인되지 않았다」·「~로 보이나」.

### 7절 이력

| 날짜 | 무엇 | 경로 |
|---|---|---|

정본은 `{연도}\` 폴더다. 이 표는 **찾아가는 입구**이지 이력 자체가 아니다.
받은 문서가 있으면 마지막 줄에 `manual\` 을 건다.

## 8,000자를 넘으면

**넘긴 채로 두지 않는다.** 읽는 순서 3번이라 매 세션 컨텍스트에 올라가고,
길어질수록 정작 1·6절이 뒤로 밀린다.

덜어내는 순서가 정해져 있다. **위에서부터 덜어낸다.**

    1  3절의 전수 목록      정본이 소스에 있다. 묶음과 개수만 남기고 실물 경로로 보낸다
    2  7절의 오래된 행       정본이 {연도}\ 폴더에 있다. 최근 것만 남긴다
    3  2절의 서술            표나 화살표 한 줄로 줄인다
    4  4절의 부연            표 안으로 넣는다

**1절과 6절은 마지막까지 줄이지 않는다.** 그 둘이 이 문서를 읽는 이유다 —
공정을 모르면 나머지가 다 있어도 쓸모가 없고, 함정은 다른 어디에도 안 적힌다.

넷을 다 해도 넘으면 **시스템이 하나가 아닌 것**을 의심한다.
`{시스템}\` 을 쪼갤 때가 된 것이지 문서를 더 줄일 때가 아니다.
