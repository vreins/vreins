# 시스템 개요 (overview.md)

> 상태: 작성완료
> 준수 강도: 권장 — 목차 구조는 필수, 표현은 자유
> 최종갱신: 2026-10-01

`wiki\{시스템유형}\{시스템코드}\{시스템코드}-OVERVIEW.md` 를 이 목차대로 쓴다. **절 구성의 정본은 이 파일 하나다.**
파일 이름에 시스템코드가 붙는 이유 — 전부 `overview.md` 였을 때 열둘이 같은 이름이라
옵시디언에서 `[[SPRG]]` 가 해결되지 않았고 그래프에 선이 안 그어졌다.

한때 위키 `readme.md` 에도 절 목록이 있었다. 그쪽이 5절로 굳는 동안 실물은 7절로 자랐고,
훅 주입문과 스킬 여섯이 전부 절 번호로 지시를 내리는데 모든 `overview.md` 가 틀린 목록을
규약이라고 가리키고 있었다. 그래서 한 곳만 남겼다. 두 벌이면 한쪽이 낡고, 낡은 쪽이 더 오래 간다.

**지금 절은 여섯이다.** 7절 「관련 이력」은 2026-09-22 에 없앴다. 그 표가 주던 날짜·제목·경로가
`ls {대역}\` 에 전부 들어 있었다. 손으로 적는 칸이었고, 손으로 적는 칸은 안 적히거나 굳는다.

## 용도

**그 시스템 하나의 현재 모습이다. 사실이지 지침이 아니다.**

    wiki\{유형}\COMMON\_manual\{기술기반}-*.md   규칙.   어긋나면 이쪽이 이긴다
    wiki\{유형}\{코드}\{코드}-OVERVIEW.md         배경.   규칙을 덮지 못한다

읽는 순서에서 **3번**이다. 시스템 정의가 어느 시스템인지 정하고 기술기반 지침이 무엇을 지킬지
정한 다음, 이 문서가 「여기는 어떤 곳인가」를 준다. 그래서 여기 적은 것이 지침과 부딪히면
지침이 이긴다. 부딪힌다는 사실 자체는 5절에 적는다.

## 머리말

```yaml
---
type: overview
system: ABCD
lifecycle: production
description: A공정 B라인 LEVEL2 — L1(PLC)↔L2↔L3(MES) 송수신·트래킹·번들 실적
owner: A공정B라인담당
techbase: [Acme_Level2_UI, Acme_Level2_TASK]
related: ["[[MESD]]", "[[ABCG]]", "[[LINK]]", "[[ABCI]]"]
updated: 2026-09-22
---
```

| 칸 | 값 | 왜 있나 |
|---|---|---|
| `lifecycle` | `skeleton` · `production` · `deprecated` | 옛 `status` 자리다. `status` 는 47개 파일이 전부 같은 값이라 정보가 0이었다 — 「작성완료/부분작성」은 절마다 다른데 파일 하나에 값 하나를 붙이면 언제나 거짓말이 된다 |
| `description` | 한 줄 | 이 시스템을 한 줄로 고를 근거다. 없으면 목록에서 고를 수 없다 |
| `owner` | 역할명 한 덩어리 — `A공정담당` | **사람 이름을 안 적는다.** 사람은 바뀌고 역할은 안 바뀐다. 누가 그 역할인지는 위키 밖(조직도)이 안다 |
| `techbase` | `[Acme_Level2_UI]` | 위키 `{유형}\COMMON\_manual\{기술기반}-*.md` 의 파일명 앞부분 그대로. **값이 곧 파일명이다** — `acme-lv2-ui` 처럼 줄이면 지침을 못 찾는다 |
| `related` | `["[[ABCD]]", …]` | **엮인 시스템 이름만.** 어떻게 엮였는지는 **2절**이 갖는다 |

### `related` 는 왜 이름만 갖나

값 전체가 `[[...]]` 라야 옵시디언이 링크로 잡는다. 그래야 그래프에 선이 그어지고
**백링크**가 생긴다 — 상대 문서에서 「누가 나를 가리키나」로 보이므로, 한쪽을 빠뜨려도 드러난다.
그리고 짧아야 **세션 시작에 훅이 통째로 밀어 넣을 수 있다**
(`hooks\scripts\lib\hook-common.ps1` 의 `Get-VreinsRelatedBlock`).

긴 설명을 여기 넣었다가 뺐다. 값 안의 `:17003` 같은 콜론이 YAML 을 깨뜨렸다.
**고치다 깨지는 형식은 안 고쳐진다.**

## 절 다섯

```
1. 시스템 개요      무엇을 하는 곳인가. 화면 목록이 아니라 하는 일
2. 연계 시스템      어느 시스템과 붙나. related 상세 표가 여기 있다
3. 처리 흐름        이 시스템 안에서 소재나 데이터가 어떻게 도나
4. 유의사항         실측으로 나온 것만. 지어내지 않는다
5. 구성 정보        저장소 · DB · 받은 문서 · 이력 · 규모 · 지침과 다른 것
```

한때 일곱이었고 그다음 여섯이었다. 2026-09-22 에 다섯으로 줄였다.
「화면·태스크 구성」과 「기술기반 지침과 다른 예외」는 절을 차지할 만큼 크지 않아
5절 안으로 넣었고, 「관련 이력」은 표가 주던 것이 `ls {대역}\` 에 다 있어 없앴다.

### 1절 — 시스템 개요

「무슨 화면이 있다」가 아니라 **무엇을 하는 곳인가**를 적는다. 화면은 5절 규모가 갖는다.
이것이 비면 나머지가 다 있어도 처음 온 사람은 아무것도 모른다.

대개 소스에서 안 나온다. 담당자에게 물어야 채워지므로, 모르면 아래 형식을 쓴다.

    <!-- UNWRITTEN -->

    **누구에게 물어야 채워지나** — {누구}. {무엇을 먼저 물어야 하는지}

뒷줄이 이 표식의 핵심이다. 빈 절은 언젠가 채워지지 않는다.
**채울 사람이 적혀 있어야 채워진다.**

### 2절 — 연계 시스템

```markdown
## 2. 연계 시스템

| 상대 | 축 | 방향 | 접근 | 무엇으로 붙나 · 왜 위험한가 | 확인 |
|---|---|---|---|---|---|
| [[ABCH]] | 공정흐름 | 받는다 | 조회만 | DB 링크로 `V_L2_INFO@L2ABCH` 를 읽는다 | 2026-09-22 TFS 실측 |
```

**이 표의 상대 목록은 머리말 `related` 와 같아야 한다.** 머리말이 「누구와」를 갖고
이 표가 「어떻게」를 갖는다. 머리말에 있는데 표에 없으면 어긋난 것이다.

칸의 말은 `wiki\관계.md` 에서 고른다. 세 묶음을 공백으로 나열한다.

```
축     공정흐름 · 층구분 · 경유 · 데이터참조 · 모듈사본 · 번호충돌 · 기능중복
방향   준다 · 받는다 · 양방향                 이 파일 기준
접근   조회만 · 쓰기                          읽기만 하나 고치기도 하나
```

축은 닫힌 목록이 아니다. 맞는 말이 없으면 새로 쓰고 `관계.md` 에 한 줄 더한다.
쓰기만 하고 안 적으면 다음 사람이 같은 뜻을 다른 말로 쓴다.

**접근 두 값의 차이가 제일 크다.** `조회만` 이면 상대가 바뀔 때 내가 깨지고,
`쓰기` 면 내가 상대를 깨뜨릴 수 있다. B공정 전처리(`ABCH`)가 B공정 테이블에
`INSERT`·`DELETE` 하는 것이 그 예다 — 빌드 의존이 0건이라 컴파일러가 안 잡는다.

양쪽 파일에 적는다. `축`과 `무엇으로`는 같고 `방향`과 `접근`만 뒤집힌다.
축을 `전공정`/`후공정` 으로 쪼개지 않는 이유가 이것이다. 낱말이 둘이면 반대쪽에 적을 때
바꿔야 하고, 바꾸는 자리마다 어긋난다.

**「없음」도 값이다.** 안 붙어 있다는 것을 적어 두지 않으면 다음 사람이 또 찾는다.
B공정에서 A공정으로 소재가 흐르는데 소스 수준 연결은 0건이고 MES 를 경유한다 —
그것을 적어 둔 덕에 DB 링크를 찾는 데 하루를 안 쓴다.

### 4절 — 유의사항

**소스를 그대로 읽으면 틀리게 되는 자리**를 적는다. 컴파일러도 검사도 안 잡고,
누가 한 번 데어 봐야 나오는 것들이다.

    같은 테이블에 두 태스크가 INSERT 하는데 컬럼 수가 37 과 58 로 다르다
    머리 주석은 52 를 세는데 SQL 은 58 을 넣는다 — 주석을 세지 말고 SQL 을 세라
    MOBI2000~2414 44개만 테이블 주석이 0% 다 — 이름으로 뜻을 짐작할 수 없다

다섯 절 가운데 **이것만 사라지면 복원되지 않는다.** 정의는 담당자가 알고, 연결은
소스에서 포트와 DB 링크를 훑으면 나오고, 흐름은 파일 이름 순서로 복원되고,
어디에 있나는 `ls` 와 `git` 이 준다. 겪은 사람이 안 적으면 다음 사람이 또 판다.

**지어내지 않는다.** 그럴듯한 추측을 적어 두면 다음 사람이 그것을 사실로 읽는다.
아직 없으면 없다고 적는다. 추측을 적고 싶으면 추측이라고 적는다 —
「확인되지 않았다」·「~로 보이나」.

### 5절 — 구성 정보

| 항목 | 값 |
|---|---|
| 저장소 | |
| techbase | 시스템 정의의 `systemBase` 와 같은지 밝힌다 |
| 형상관리 | TFS · git · svn · 없음 |
| DB | |
| 서버 경로 | |
| 받은 문서 | `_manual\{코드}-INDEX.md` 로 가는 링크 하나. 목록은 그쪽이 갖는다 |
| 소유자 | |

모르는 칸은 비우지 말고 `<!-- UNWRITTEN -->` 와 **모르는 이유**를 적는다.
「권한 밖이라 못 본다」와 「아직 안 물어봤다」는 다음에 할 일이 다르다.

아래 둘을 `###` 로 붙인다.

```
### 기술기반 지침과 다른 것    없으면 「없음」 한 줄. 본문은 지침 쪽에 적고 여기는 위치만
### 규모                      화면·태스크 개수. 정본은 소스라 반드시 낡는다
```

### 5절 — 이력은 기계가 채운다

```markdown
### 이력
<!-- auto:이력  손으로 고치지 않는다. 생성기가 ls 로 채운다 -->
- 2610-TS-등급미표시
- 2609-SR2609-0001-등급컬럼추가
<!-- /auto -->
```

폴더명에 날짜·SR번호·제목이 다 들어 있어(실측 제목 100% · 날짜 92% · SR번호 67%)
**한 줄 요약을 또 붙이지 않는다.** 폴더명만 쓰면 100건이 2,500자다 — 8,000자 안에 든다.
요약까지 붙이면 5,500자가 되어 큰 시스템에서 터진다.

100건이 넘으면 **`pin` 찍힌 것과 최근 순**으로 100건을 유지한다.
남길 것은 그 작업의 `readme-{SR번호}.md` 머리말에 `pin: true` 를 적어 표시한다.
**사람은 판단만 하고 목록은 기계가 쓴다** — 손으로 적는 칸은 안 적히거나 굳는다.

## 8,000자를 넘으면

넘긴 채로 두지 않는다. 읽는 순서 3번이라 매 세션 컨텍스트에 올라가고, 길어질수록
정작 1·6절이 뒤로 밀린다.

덜어내는 순서가 정해져 있다. **위에서부터 덜어낸다.**

    1  5절 규모의 전수 목록   정본이 소스에 있다. 묶음과 개수만 남기고 실물 경로로 보낸다
    2  3절 흐름의 서술        표나 화살표 한 줄로 줄인다
    3  5절의 부연            표 안으로 넣는다

**1절과 4절은 마지막까지 줄이지 않는다.** 그 둘이 이 문서를 읽는 이유다.
공정을 모르면 나머지가 다 있어도 쓸모가 없고, 유의사항을 적는 자리는 4절 말고 없다.

셋을 다 해도 넘으면 **시스템이 하나가 아닌 것**을 의심한다.
`{시스템}\` 을 쪼갤 때가 된 것이지 문서를 더 줄일 때가 아니다.

## 여기 적지 않는 것

| 무엇 | 어디에 |
|---|---|
| 지침·규칙 | `wiki\{유형}\COMMON\_manual\{기술기반}-*.md`. 시스템별 예외조차 그쪽 본문의 표에 적는다 |
| SR 이력 **요약** | 폴더명이 이미 날짜·번호·제목을 갖는다. 5절 자동구역엔 폴더명만 |
| 받은 문서 목록 | `{시스템}-INDEX.md`. 5절에는 링크 하나만 |
| 소스 사본 | 체인지셋이 정본이다. 사본을 두면 정본이 둘이 된다 |
