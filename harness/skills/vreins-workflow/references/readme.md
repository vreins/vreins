# readme — 작업 폴더 표지

> 상태: 부분작성
> 준수 강도: 권장 — 목차 구조는 필수, 표현은 자유
> 최종갱신: 2026-09-21

작업 폴더마다 하나씩 있다. **단계 산출물이 아니라 그 폴더가 무엇인지 말하는 표지다.**

파일 이름은 `readme-{제목}.md` 다. `{제목}` 은 단계 문서와 같다 —
작업 폴더 이름에서 날짜·SR번호를 뗀 나머지고, 밑줄은 하이픈으로 바꾼다.

```
2601-SR2601-00001-조회조건추가\
  readme-조회조건추가.md
  01-requirements-조회조건추가.md
  02-analysis-조회조건추가.md
  ...
```

## 세션을 열 때 먼저 만든다

**폴더만 만들고 단계 문서부터 쓰지 않는다.** 표지가 없으면 그 폴더가 무엇인지
목차가 집지 못한다.

## 머리말

```yaml
---
type: srs
id: SR2601-00001
system: ABCD
techbase: [Acme_Level2_UI, Acme_Level2_TASK]
화면코드: [ABCD100E01]     # 고친 화면. 없으면 빼지 말고 [] 로 둔다
화면대역: "100"            # 화면코드 5~7자리
description: 한 줄 요약     # 목차가 이걸 긁어 간다
updated: 2026-09-21
---
```

작업이 끝나면 더한다.

```yaml
closed: 2026-09-30
```

**번호가 아직 없으면 `id` 를 폴더 이름에서 끌어온다** — `{구분}-{제목}`.

```
2610-TS-화면응답지연장애        →  id: TS-화면응답지연장애
2609-SR-채번체계변경            →  id: SR-채번체계변경
```

`미정` · `TBD` 같은 값을 넣지 않는다. **목차가 그것으로 문서를 집는다.**
번호가 나오면 폴더 이름과 `id` 를 같이 바꾼다.

`type` 은 둘뿐이다.

```
srs    우리가 진행하는 SR · SM · TS
fact   남이 쓴 기록을 받아 온 것. 아래 참조
```

## 본문

```markdown
# {작업 폴더 이름}

## 무슨 작업인가
한두 문장. 상세는 01·02 가 갖는다.

## 산출물
| 단계 | 문서 |
|---|---|

## 진행
지금 어디까지 왔나. **단계 문서가 있느냐가 정본이고 여기는 사람이 읽는 요약이다.**
```

**여기에 업무 내용을 길게 쓰지 않는다.** 표지가 두꺼워지면 단계 문서를 안 읽게 된다.

## 받아 온 기록

남이 쓴 문서를 옮겨 온 경우 `type: fact` 로 하고 **출처를 반드시 남긴다.**

```yaml
type: fact
출처:
  저장소: "http://{git-서버}/{위키-저장소}.git"
  경로: domain/{도메인}/modules/{모듈}/troubleshooting/2026-06-29-....md
  작성자: {작성자}
```

본문에는 **무엇을 손댔는지** 적는다 — 파일 이름 매핑, 링크 재지정, 원본에 없던
키를 더한 것. **맞춤법·표현·문장은 건드리지 않는다.** 남의 글이다.

우리 값 집합 밖의 키는 지우지 말고 이름만 바꿔 남긴다 (`status:` → `원본status:`).

실물이 갈린다. 5단짜리 SR 의 표지에는 `영향범위` · `변경예정파일` · `체인지셋` 이
없고, TS 한 장짜리 표지에는 있다.

정본은 그 값을 만든 단계 문서다 — 영향범위는 02, 변경예정파일은 03, 체인지셋은 06.
**표지에 같이 적으면 어긋날 자리가 생긴다.** 어긋나서 옛 상태 파일을 없앴다 —
실측 41건 중 37건(90%)이 기록된 완료단계와 실제 산출물이 달랐다.

**누구에게 물어야 채워지나** — 위키 담당(sye). 목차 생성기가 표지만 읽는지,
단계 문서까지 읽는지가 첫 질문이다. 생성기가 표지만 읽으면 사본이 필요하고,
단계 문서를 읽으면 표지에 두면 안 된다.
