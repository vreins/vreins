# 단계대로 진행하고 남긴다

> 상태: 작성완료
> 준수 강도: 필수
> 최종갱신: 2026-09-21
> 출처: 우리가 쓴 것. superpowers 파생 아님

## 이 스킬이 있는 이유

산출물이 wiki 에 쌓이게 만드는 것은 사람이 기억하는 것이 아니라 **이 절차다.**
단계가 끝나면 그 단계의 문서가 **생긴다.** 물어보고 만들지 않는다.

## 시작 전에 확인하는 셋

| 무엇 | 없으면 |
|---|---|
| 시스템 | `vreins-system` 스킬이 확정한다. 그것도 못 찾으면 멈춘다 |
| 세션 폴더 | 만든다 — `{wiki}\{유형}\{코드}\{화면대역}\{YYMM}-{구분}-{제목}\`<br>그 안에 `readme-{제목}.md` 를 **먼저** 만든다 |
| 그 단계의 기술기반 지침 | **없다고 보고하고 멈춘다.** 다른 것으로 대신하지 않는다 |

세션 밖에서 시스템코드를 고치지 않는다. **이력이 안 남는 작업은 하지 않는다.**

## 차선 넷 — 작업 크기에 맞춘다

**모든 작업에 여섯 단계를 요구하지 않는다.** 무거우면 사람이 절차를 지키는 대신
중간에 버린다 — 위키 전체에서 06 까지 간 작업이 두 건이다.

```
정식   01 → 02 → 03 → 04 → 05 → 06      기본값
간이   01 → 23 → 04 → 05 → 06            분석과 설계가 한 장
단건   한 장                              승인 한 번. [[단건]]
TS     한 장                              장애
```

**작은 것부터 본다.** 단건이 되면 단건, 아니면 간이, 그것도 아니면 정식이다.

```
단건   파일 하나 · 새 동작 없음 · 공통 모듈과 DB 스키마 무접촉 · 해석이 안 갈림
간이   화면 하나 · 기술기반 하나 · 새 파일 없음 · DB 스키마와 공통 모듈 무접촉
```

**일의 크기와 무관하게 같은 값을 물리지 않는다.** 라벨 한 줄에 여섯 단계를 돌면
사람은 절차를 지키는 대신 피하고, 그러면 작은 건이 하네스 밖에서 처리된다.

**판정은 분석 단계 들머리에서 한다.** 코드를 한 번 훑고 정한 뒤 표지 머리말에 적는다.

```yaml
lane: single    # 단건
lane: quick     # 간이
                # 없으면 정식
```

**단건만 01 전에 판정한다.** 한 장으로 끝날 건에 01 을 따로 쓰는 것이 이미 과하다.
대신 **갈릴 것이 하나라도 보이면 그 순간 단건이 아니다** — 물을 것이 생겼다는 건
요구가 확정되지 않았다는 뜻이고, 그건 01 이 할 일이다.

**01 끝에 정하지 않는다.** 뒤의 둘(새 파일·공통 모듈)은 **코드를 봐야 아는데
01 은 코드를 보지 않는다.** 실측에서 01 이 간이로 판정했다가 02 에서 뒤집혀
표지를 다시 쓰고 01 에 각주를 다는 되돌리기가 났다. 판정할 수 없는 자리에서
판정하지 않는다.

**단건·간이 중에 조건을 벗어나면** 멈추고 보고한 뒤 한 단 위로 올린다. 쓴 것은 두고
남은 단계부터 정식으로 간다. 그 사실을 표지 「진행」에 한 줄.

## 단계와 양식

```
01  Requirements    무엇을 해달라는 것인가를 확정한다      코드를 안 본다
02  Analysis        우리 코드에서 무슨 뜻인가              코드를 본다
03  Design          무엇을 어떻게 바꿀 것인가
23  Analysis·Design 간이 차선. 02 와 03 을 한 장으로
단건                 한 장. 파일 하나 · 새 동작 없음 · 승인 한 번
04  Development     고친다
05  Testing         확인한다
06  Deployment      올린다. 올릴 것이 없으면 표지에 「해당 없음」 한 줄

TS  Troubleshooting 한 장으로 끝낸다. 단계를 나누지 않는다
```

양식은 `references\` 에 있다. **절을 하나도 빼지 않는다.**

```
references\_공통.md               파일명·머리말·빈 절. 모든 양식이 공유한다
references\_간결.md               줄 수 한도와 원시인 규칙 일곱. 린터가 집행한다
references\readme.md              작업 폴더 표지. 세션을 열 때 먼저 만든다
references\01-requirements.md  ~  06-deployment.md
references\23-analysis-design.md  간이 차선 전용
references\단건.md                단건 차선 전용. 한 장
references\TS-troubleshooting.md
references\overview.md            시스템 배경 6절. 단계 산출물이 아니다
```

## 짧게 쓴다 — 한도가 있다

**분량은 성실함의 증거가 아니다.** 문서마다 줄 수 한도가 있고 **린터가 센다.**
정본은 [[_간결]] 이고 여기서는 표만 옮긴다.

```
readme 25  ·  01 45  ·  02 50  ·  03 50  ·  23 70  ·  단건 25
04 45  ·  05 50  ·  06 30  ·  TS 70        (본문 줄. 머리말은 안 센다)
```

**한 번 쓰고 깎지 않는다.** 넘었으면 그 사실을 한 줄 적고 넘어간다 —
깎는 일은 새로 아는 것이 없는 재작업이다. 다음에 짧게 쓰면 된다([[_간결]]).

전에는 이 자리에 「짧게 쓴다」가 **권고**로 있었고, 그 상태로 잰 산출물이
문서 다섯에 522줄이었다. **권고는 안 지켜진다.**

```
결론 먼저              절의 첫 줄이 답이다
문장보다 표            줄글은 같은 내용에 세 배를 쓴다
수식어 금지            매우 · 상당히 · ~하는 것이 좋다 · ~인 것으로 보인다
설명 대신 좌표         파일:줄 이 세 문단을 이긴다
코드를 옮기지 않는다     소스가 정본이다. 설계든 개발이든 같다
앞 문서를 요약하지 않는다  번호로 건다. 옮겨 적으면 한쪽이 낡는다
모르면 묻는다           추측을 문장으로 채우지 않는다. 표에는 답만 남는다
```

**마지막이 제일 크다.** 해석 후보 셋을 설명하면 12줄, 물어보면 1줄이다.

## 단계별 로딩

`vreins-rules` 스킬의 표가 정본이다. 분석 단계 문서(`02-analysis-*` 또는
간이 차선의 `23-analysis-design-*`) 머리말의 `영향범위` 로
좁힌 기술기반(`{기술기반 루트}\{기술기반}-*.md`)에서 그 단계가 `O` 한 것만 읽는다.

**`상태: 미작성` 인 파일은 읽지 않은 것으로 친다.** 없는 것과 같다.

## 단계 종료 순서

```
1  양식대로 산출물을 쓴다        절을 빼지 않는다. 머리말도 채운다
2  사용자에게 보고하고 승인받는다
3  승인 후 커밋한다
4  다음 단계를 바로 이어서 시작한다
```

**머리말은 본문과 같이 쓴다.** 영향범위 · 변경예정파일 · 체인지셋은 그 단계 문서의
머리말에만 있다 — 거기 안 적으면 다음 세션이 그 값을 찾을 자리가 없다.

**2번 전에 커밋하지 않는다.**

### 위키가 안 추적하는 자리면 3번을 건너뛴다

실습(`TEST/SEDU/`)처럼 위키가 `.gitignore` 로 빼 둔 자리가 있다. 거기서 `git add`
하면 **아무 일도 안 일어나고 커밋은 비어서 실패한다** — 그걸 오류로 읽고 멈추거나,
`-f` 로 밀어 넣으면 안 된다.

```
git check-ignore -q {세션 폴더}    걸리면 커밋하지 않는다
```

**건너뛴 사실을 보고한다.** 「커밋했다」고 말하지 않는다. 산출물은 디스크에 있고,
그 자리는 원래 이력을 안 남기기로 한 곳이다.

### 4번 — 사람이 커맨드를 다시 치게 하지 않는다

승인은 **「이 단계가 맞다」**는 뜻이고, 거기엔 다음 단계로 가도 된다는 뜻이 들어 있다.
그러니 승인을 받으면 **다음 단계를 그 자리에서 시작한다.** 「다음은 `/vreins-analysis`
입니다」라고 알려 주고 멈추지 않는다 — 그건 사람에게 절차를 외우게 하는 것이다.

한 번에 한 단계씩 간다. **앞 단계 승인 없이 두 단계를 묶어 쓰지 않는다** —
승인이 사라지면 요구가 틀린 채로 설계까지 쌓인다.

멈추는 자리는 셋뿐이다.

```
승인이 안 났다            고칠 것을 듣고 그 단계를 다시 쓴다
그 단계의 기술기반 지침이 없다   없다고 보고하고 멈춘다
사람이 그만하자고 했다
```

마지막 단계(06 배포, 또는 그 작업에서 해당 없는 단계의 직전)에서는 더 가지 않는다.

**상태 파일을 따로 두지 않는다.** 어디까지 했나는 **그 단계 문서가 있느냐**가 말한다.
따로 적어 두면 어긋난다 — 실제로 Standard 41건 중 37건(90%)이 기록된 완료단계와
실제 산출물이 달랐다.

끝났다고 말하기 전에 `vreins-verify` 스킬을 쓴다. 근거 없이 완료를 말하지 않는다.

## 빈 절

셋 중 하나를 적는다.

```
내용                 쓸 것이 있다
「해당 없음」          그 항목이 이 작업에 없다는 판단
<!-- UNWRITTEN -->   알아야 하는데 아직 모른다
```

**빈 절은 누락과 해당 없음이 구분되지 않는다.** 구분되지 않으면 둘 다 조용히 넘어간다.

## 영향범위

분석 단계가 판정해 **그 문서 머리말**에 적는다 — 정식이면 `02-analysis-{제목}.md`,
간이면 `23-analysis-design-{제목}.md`. 이후 단계는 **그것만** 읽는다.

**차선이 갈려도 영향범위가 사는 자리는 늘 있다.** 간이가 02 를 없애는 것이 아니라
02 와 03 을 한 장으로 합치는 것이라, 판정도 머리말도 그 한 장이 갖는다.

```yaml
techbase: [Acme_Level2_UI, Acme_Level2_TASK]
영향범위: [Acme_Level2_UI]
```

설계·개발 중 영향범위 **밖의 파일**이 나오면 그 자리에서 멈춘다.

```
멈춘다 → 사용자 확인 → 영향범위 확대 → 분석 문서 머리말 갱신
       → 넓어진 기술기반 지침을 그 자리에서 읽는다 → 계속
```

**마지막이 핵심이다.** 영향범위를 넓히는 것은 「파일 하나 더」가 아니라
**읽어야 할 지침이 한 벌 더 생기는 것**이다.
확대 이력은 설계 문서(`03-design-*` 또는 `23-analysis-design-*`)에 한 줄 남긴다.

**간이 차선이었으면 확대가 곧 차선 이탈이다** — 기술기반이 둘이 된 순간
간이 조건을 벗어난다. 정식으로 돌리고 표지 「진행」에 적는다.

## 코드를 만지기 전에

`wiki\{유형}\COMMON\_manual\{영향범위}-Linter.md` 를 **읽었는지 확인한다.**
안 읽었으면 만지지 않는다. 4종 중 준수 강도가 「필수」인 것은 이것뿐이다.

형상관리에 따라 준비가 다르다.

```
TFS   편집 전 체크아웃한다. 안 하면 편집 자체가 실패한다
git   브랜치 없이 작업한다. 커밋은 마지막에
```

## 끝났다고 말할 조건

- 그 단계 산출물의 절이 비어 있지 않다
- 머리말이 다 채워졌다 — 특히 `영향범위`(02) · `변경예정파일`(03) · `체인지셋`(06)
- 「필수」 지침을 안 어겼거나, 어겼다면 멈추고 보고했다
- 못 한 것이 있으면 **그 사유가 문서에 적혀 있다**

빠진 것을 덮지 않는다. **안 된 것은 안 됐다고 쓴다.**
