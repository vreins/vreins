# 단계대로 진행하고 남긴다

> 상태: 작성완료
> 준수 강도: 필수
> 최종갱신: 2026-09-21
> 출처: 우리가 쓴 것. superpowers 파생 아님

## 이 스킬이 있는 이유

산출물이 wiki 에 쌓이게 만드는 것은 사람이 기억하는 것이 아니라 **이 절차다.**
단계가 끝나면 그 단계의 문서가 **생긴다.** 물어보고 만들지 않는다.

## 시작 전에 확인하는 셋

| 무엇 | 없으면 |
|---|---|
| 시스템 | `vreins-system` 스킬이 확정한다. 그것도 못 찾으면 멈춘다 |
| 세션 폴더 | 만든다 — `{wiki}\{유형}\{코드}\{연도}\{YYMM}-{구분}-{제목}\`<br>그 안에 `readme-{제목}.md` 를 **먼저** 만든다 |
| 그 단계의 기술기반 지침 | **없다고 보고하고 멈춘다.** 다른 것으로 대신하지 않는다 |

세션 밖에서 시스템코드를 고치지 않는다. **이력이 안 남는 작업은 하지 않는다.**

## 단계와 양식

```
01  Requirements    무엇을 해달라는 것인가를 확정한다      코드를 안 본다
02  Analysis        우리 코드에서 무슨 뜻인가              코드를 본다
03  Design          무엇을 어떻게 바꿀 것인가
04  Development     고친다
05  Testing         확인한다
06  Deployment      올린다

TS  Troubleshooting 한 장으로 끝낸다. 단계를 나누지 않는다
```

양식은 `references\` 에 있다. **절을 하나도 빼지 않는다.**

```
references\readme.md              작업 폴더 표지. 세션을 열 때 먼저 만든다
references\01-requirements.md  ~  06-deployment.md
references\TS-troubleshooting.md
references\overview.md            시스템 배경 6절. 단계 산출물이 아니다
```

## 단계별 로딩

`vreins-rules` 스킬의 표가 정본이다. `02-analysis-{SR번호}.md` 머리말의 `영향범위` 로
좁힌 기술기반(`{기술기반 루트}\{기술기반}-*.md`)에서 그 단계가 `O` 한 것만 읽는다.

**`상태: 미작성` 인 파일은 읽지 않은 것으로 친다.** 없는 것과 같다.

## 단계 종료 순서

```
1  양식대로 산출물을 쓴다        절을 빼지 않는다. 머리말도 채운다
2  사용자에게 보고하고 승인받는다
3  승인 후 커밋한다
```

**머리말은 본문과 같이 쓴다.** 영향범위 · 변경예정파일 · 체인지셋은 그 단계 문서의
머리말에만 있다 — 거기 안 적으면 다음 세션이 그 값을 찾을 자리가 없다.

**2번 전에 커밋하지 않는다.**

**상태 파일을 따로 두지 않는다.** 어디까지 했나는 **그 단계 문서가 있느냐**가 말한다.
따로 적어 두면 어긋난다 — 실제로 Standard 41건 중 37건(90%)이 기록된 완료단계와
실제 산출물이 달랐다.

끝났다고 말하기 전에 `vreins-verify` 스킬을 쓴다. 근거 없이 완료를 말하지 않는다.

## 빈 절

셋 중 하나를 적는다.

```
내용                 쓸 것이 있다
「해당 없음」          그 항목이 이 작업에 없다는 판단
<!-- UNWRITTEN -->   알아야 하는데 아직 모른다
```

**빈 절은 누락과 해당 없음이 구분되지 않는다.** 구분되지 않으면 둘 다 조용히 넘어간다.

## 영향범위

분석 단계가 판정해 **`02-analysis-{제목}.md` 머리말**에 적는다.
이후 단계는 **그것만** 읽는다.

```yaml
techbase: [Acme_Level2_UI, Acme_Level2_TASK]
영향범위: [Acme_Level2_UI]
```

설계·개발 중 영향범위 **밖의 파일**이 나오면 그 자리에서 멈춘다.

```
멈춘다 → 사용자 확인 → 영향범위 확대 → 02-analysis 머리말 갱신
       → 넓어진 기술기반 지침을 그 자리에서 읽는다 → 계속
```

**마지막이 핵심이다.** 영향범위를 넓히는 것은 「파일 하나 더」가 아니라
**읽어야 할 지침이 한 벌 더 생기는 것**이다.
확대 이력은 `03-design-{제목}.md` 에 한 줄 남긴다.

## 코드를 만지기 전에

`wiki\{유형}\COMMON\techbase\{영향범위}-Linter.md` 를 **읽었는지 확인한다.**
안 읽었으면 만지지 않는다. 4종 중 준수 강도가 「필수」인 것은 이것뿐이다.

형상관리에 따라 준비가 다르다.

```
TFS   편집 전 체크아웃한다. 안 하면 편집 자체가 실패한다
git   브랜치 없이 작업한다. 커밋은 마지막에
```

## 끝났다고 말할 조건

- 그 단계 산출물의 절이 비어 있지 않다
- 머리말이 다 채워졌다 — 특히 `영향범위`(02) · `변경예정파일`(03) · `체인지셋`(06)
- 「필수」 지침을 안 어겼거나, 어겼다면 멈추고 보고했다
- 못 한 것이 있으면 **그 사유가 문서에 적혀 있다**

빠진 것을 덮지 않는다. **안 된 것은 안 됐다고 쓴다.**
