# 작업 규칙

> 상태: 작성완료
> 준수 강도: 필수
> 최종갱신: 2026-09-22
> 출처: 우리가 쓴 것. superpowers 파생 아님

하네스의 헌법. **무엇을 언제 읽고, 언제 멈추는지**를 정한다.

## 1. 로딩 순서

**세션 시작에 훅이 넣는 것 — 넷.**

    1  skills\vreins-rules\SKILL.md       이 문서 (전문)
    2  {레지스트리}\systems.md            이 시스템 행만 — 위치는 3절
    3  {위키}\glossary.md                 용어 색인만
    4  hooks\rules\handling-unknowns.md   시점을 안 가리는 규칙

**그 뒤에 조건이 맞을 때 들어오는 것.**

    {기술기반 루트}\{영향범위}\   영향범위가 정해진 뒤. 4절 표가 O 한 것만
    hooks\rules\ 나머지          편집·커밋처럼 그 순간에만 의미가 있는 것

없는 파일은 건너뛴다. `상태: 미작성` 은 읽지 않은 것으로 취급한다.

`systems.md` 의 모듈 코드 조회표와 `reference-*.md` 는 **자동 로딩하지 않는다.**
필요한 자리에서 명시적으로 부른다.

## 커맨드와 스킬

**둘은 부르는 주체가 다르다.** 2026-09-22 회의로 갈랐다.

`commands\` — **사람이 친다.** 하네스에 들어오는 문 여덟이다.

    /vreins-requirements    01  무엇을 해달라는 것인가
    /vreins-analysis        02  우리 코드에서 무슨 뜻인가 · 영향범위를 정한다
    /vreins-design          03  무엇을 어떻게 바꿀 것인가
    /vreins-development     04  고친다
    /vreins-testing         05  확인한다
    /vreins-deployment      06  올린다 · 체인지셋을 남긴다
    /vreins-troubleshoot    TS  장애. 한 장으로 끝낸다
    /vreins-review              체크인·PR 전에 훑는다 · 지적을 처리한다

`skills\` — **AI 가 부른다.** 세션 시작에 올라가지 않고 **그 상황이 되면** 부른다.

    vreins-workflow   단계를 진행하고 산출물을 남길 때 — 커맨드 여섯이 이걸 쓴다
    vreins-system     지금 다루는 코드베이스·경로·기술기반을 확정할 때
    vreins-plan       설계를 쓸 때 — 어느 정도로 구체적이어야 하나
    vreins-debug      버그·장애를 만났을 때
    vreins-review     리뷰를 요청하거나 지적을 받았을 때
    vreins-verify     끝났다고 말하기 직전에

**커맨드는 얇다.** 절차·양식·멈추는 조건은 전부 스킬이 정한다 —
두 군데 적으면 한쪽이 낡는다.

**폴더로는 더 못 나눈다.** `commands\` 는 하위 폴더를 안 읽고 `skills\` 는
한 단계까지다. 그래서 `vreins-` 앞가지로 묶는다.

## 2. 미작성 표식

| 표식 | 하네스 동작 |
|---|---|
| 미작성 | 읽지 않은 것과 동일하게 취급 |
| 부분작성 | 읽되 `<!-- UNWRITTEN -->` 절은 지식 없음으로 취급 |
| 작성완료 | 전체를 유효한 지침으로 취급 |

지식이 없는 자리에 판단이 필요하면 **추측하지 않고 사용자에게 확인**한다.

## 3. 기술기반 · 레지스트리 위치

**플러그인 안이 아니다.** 2026-09-22 회의로 시스템·기술기반 정보를 플러그인에서
내렸다. 플러그인은 우리 조직이 아닌 사람이 받아 써도 되는 범용 뼈대만 담고,
「우리 시스템은 무엇을 지키나」는 각자의 위키·로컬이 갖는다.

그래서 이 둘은 **찾는** 것이지 아는 것이 아니다. 먼저 잡히는 것을 쓴다.

**위키** — 여기서부터 나머지가 갈린다

    VREINS_WIKI_ROOT           런처가 넣는다
    {루트}\wiki-location.txt   **사람이 적는 자리**
    {루트}\wiki\               우리 설치기가 클론하는 기본 자리

**기술기반 루트**

    VREINS_TECHBASE_ROOT     환경변수. 있으면 이긴다
    {위키}\techbase\         정본
    {루트}\techbase\
    플러그인\techbase\        이관 전 옛 자리. 이제 없다

**레지스트리**

    VREINS_REGISTRY                                    환경변수. 있으면 이긴다
    {위키}\systems.md                                   정본
    {루트}\systems\systems.md
    플러그인\skills\vreins-system\references\systems.md  이관 전 옛 자리

`{루트}` 는 `VREINS_ROOT`, 없으면 `C:\vReins` 다.

### 사람이 고치는 자리는 하나다

위키를 자기가 세운 사람은 `{루트}\wiki-location.txt` 에 **한 줄** 적는다.

    # 이 아래 한 줄에 내 위키 폴더 경로를 적는다.
    {여기에 위키 폴더 경로를 적으세요}

**플러그인 안에 적게 하지 않는다.** 거기는 갱신 때 통째로 덮여서
적어 둔 것이 조용히 사라지고, 왜 사라졌는지 알 방법이 없다.

**중괄호가 남아 있으면 안 적은 것으로 본다.** `{…}` · `(…)` · `<…>` 로 감싼 줄은
값이 아니라 자리표시자다 — 받자마자 그대로 둔 것을 경로로 읽는 일을 막는다.

위키만 정해지면 기술기반·레지스트리는 그 안에서 따라온다.
**바깥에서 받아 쓰는 사람은 이 자리가 비어 있다** — 비면 채우라고 말하고 멈춘다.
경로를 지어내지 않는다.

### 무엇을 읽나

레지스트리의 `systemBase` 컬럼이 **어느 기술기반을 쓰는지**의 정본이다.
그 지침은 `{기술기반 루트}\{systemBase}\` 에 있고 4종이다.

    guideline-TechStack.md      언어 · 프레임워크 · DB
    guideline-Architecture.md   구조
    guideline-Boilerplate.md    복사 단위
    guideline-Linter.md         반드시 확인할 것

**그 폴더가 없거나 `상태: 미작성` 이면 없다고 보고한다.**
다른 기술기반 지침을 가져다 쓰지 않는다.

폴더는 있는데 `guideline-*.md` 가 없는 경우가 있다 — `README.md` 가
왜 비었고 누구에게 물어야 하는지를 적고 있다. **읽을 지침은 여전히 없는 것이다.**

## 4. 단계별 로딩

**이 표가 정본이다.** 각 지침 파일은 자기가 몇 단계에서 읽히는지 적지 않는다 —
두 군데 적으면 어긋난다.

| 단계 | TechStack | Architecture | Boilerplate | Linter | 위키 `overview` | 과거 이력 |
|---|---|---|---|---|---|---|
| Requirements | | | | | 1·2절 | |
| Analysis | | O | | | **5·6·7절** | **O** 같은 화면·같은 증상 |
| Design | O | O | | | 5·6절 | **O** 그 화면의 `03-design` |
| Development | O | O | O | O | **6절** | |
| Testing | O | | | O | | **O** 과거 `05-testing` 회귀 목록 |
| Deployment | O | O | | | 4절 | **O** 과거 `06-deployment` |
| Troubleshooting | O | O | | O | **6절** | **O** 과거 `01-troubleshooting` 4절 |

**Requirements 는 한 칸도 안 읽는다.** 빠뜨린 것이 아니다 — 그 단계는 코드를
보지 않고 「무엇을 해달라는 것인가」만 확정한다. 기술기반을 읽으면 요구가
정해지기 전에 구현을 생각하게 된다.

`reference-*.md` 는 이 표에 없다. **자동 로딩하지 않고 명시 호출만 한다.**

### 위키 쪽을 읽는 법

**`overview` 를 통째로 열지 않는다.** 표가 가리키는 절만 본다.
6절(이 시스템만의 함정)이 제일 자주 나오는데, **고치기 전에 아는 것**이 거기 있기 때문이다.

**과거 이력은 전문을 훑지 않는다.** `overview` 7절 표(날짜·한 줄·경로)에서
**고른 것만** 연다. 7절은 이력 자체가 아니라 **찾아가는 입구**고,
정본은 `{연도}\{작업}\` 폴더다.

| 단계 | 왜 과거를 보나 |
|---|---|
| Analysis | 이미 한 번 다뤄진 건인지 — 같은 화면·같은 증상이 있었나 |
| Design | **왜 그렇게 설계했나.** 지금 뒤집으려는 게 그때의 결정일 수 있다 |
| Testing | **회귀 테스트 목록이 거기 있다.** 제일 실용적인 이유다 |
| Deployment | 순서 · 롤백 · 그때 걸렸던 것 |
| Troubleshooting | 과거 4절 「배제한 것」 — 같은 길을 두 번 파지 않는다 |

**Development 가 이력을 안 읽는 것은 빠뜨린 게 아니다.** 구현 중에 이력을 뒤지면
손이 멈춘다. 볼 것은 03 설계에서 이미 봤다.

**이력이 0건이면 「없다」고 말하고 진행한다.** 다른 시스템 것을 가져다 쓰지 않는다 —
`related` 가 가리키는 시스템은 **「다른 층의 같은 공정」임을 밝히고** 본다.

## 5. 영향범위

기술기반이 복수인 시스템에서 한쪽만 건드리는 작업이 많다.
**분석 단계가 판정해** `02-analysis-{제목}.md` 머리말에 적고, 이후 단계는 그것만 읽는다.

```yaml
techbase: [Acme_Level2_UI, Acme_Level2_TASK]
영향범위: [Acme_Level2_UI]
```

**상태 파일을 따로 두지 않는다.** 어디까지 했나는 「그 단계 문서가 있느냐」가 말한다.
값은 그 값을 만든 문서가 갖는다 — 영향범위는 분석이, 변경예정파일은 설계가,
체인지셋은 배포가.

머리말 키는 `techbase` 다. 레지스트리 컬럼과 환경변수는 `systemBase` 인데
**같은 것을 두 이름으로 부른다** — 위키의 실물 파일이 `techbase` 라 거기에 맞췄다.
어느 쪽으로 통일할지는 아직 안 정했다.

설계·개발 중 영향범위 **밖의 파일**이 나오면 그 자리에서 멈춘다.

    경고 → 사용자 확인 → 영향범위 확대 → 02-analysis 머리말 갱신
         → 확대된 기술기반 지침을 그 자리에서 추가 로딩 → 계속

확대 이력은 `03-design-{제목}.md` 에 한 줄 남긴다. 조용히 넓히지 않는다.

    영향범위 확대: Level2_UI → Level2_UI, Level2_TASK (조회 쿼리 신규 필요)

| 관계 | 규칙 |
|---|---|
| 하네스 공통 ↔ 기술기반 | 기술기반 우선 |

## 7. 준수 강도

| 등급 | 행동 |
|---|---|
| 필수 | 위반 금지. 위반해야 요구를 만족하면 중단하고 보고 |
| 권장 | 따른다. 이탈하면 문서에 사유를 남긴다 |
| 참조 | 맥락용. 이것만으로 판단하지 않는다 |

## 8. 게이트

각 단계는 앞 단계 산출물이 **승인된 뒤에** 시작한다.
모든 단계에서 사용자 승인 후 문서를 쓰고 커밋한다.

## 9. 위키 `index.md` 는 기계가 짓는다

**손으로 고치지 않는다.** 정본은 각 `overview.md` 의 머리말이고
(`lifecycle` · `description` · `owner` · `related`), `index.md` 는 그것을 모아 찍은 표지다.
손으로 고친 줄은 다음 생성 때 사라진다 — 목차 줄이 틀렸으면
**그 시스템의 `overview.md` 머리말**을 고친다.

    목차 줄이 비었다        그 overview.md 에 description 이 없다
    위험 표에 안 뜬다       그 overview.md 에 related 가 없다
    「뼈대만」으로 분류됐다   그 overview.md 의 lifecycle 이 skeleton 이다

**`index.md` 에 SR 목록은 없다.** 없는 것이 아니라 두지 않는 것이다 —
폴더명에 날짜·SR번호·제목이 다 들어 있어 목차를 따로 지을 이유가 없다.
SR 은 이렇게 찾는다.

    폴더를 훑는다   ls {유형}\{시스템}\{연도}\
    grep           머리말 필터. 419개에 0.16초다

앞으로는 `/find` 커맨드가 이 자리를 맡는다. **지금은 없다** —
만들어질 때까지 위 둘로 찾는다. **없는 커맨드를 있는 것처럼 부르지 않는다.**
