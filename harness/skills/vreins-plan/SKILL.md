# 설계는 그대로 따라 할 수 있어야 한다

> 상태: 작성완료
> 준수 강도: 필수
> 최종갱신: 2026-09-21
> 출처: obra/superpowers 의 `writing-plans` 파생 (MIT · Jesse Vincent)
>       → `harness\LICENSE` · `harness\ATTRIBUTION.md`

## 한 줄

**이 코드를 처음 보는 사람이 그대로 따라 할 수 있게 쓴다.**

읽는 사람이 실력은 있지만 **이 시스템과 이 솔루션은 모른다**고 가정한다.
어느 파일을 · 무엇으로 · 어떻게 확인하는지까지 적는다.

양식은 `references\03-design.md` 가 갖는다. 이 스킬은 **그 칸을 어느 정도로
채워야 하는가**를 정한다.

## 파일 구조

작업을 쪼개기 전에 **어느 파일이 생기고 어느 파일이 바뀌는지** 먼저 적는다.
여기서 쪼개는 방식이 결정된다.

```
Level2 TASK   한 태스크가 한 exe 다. 프로젝트 하나가 작업 단위다
Level2 UI     화면 하나가 파일 5종이다. 무엇이 바뀌는지 종별로 적는다
공통 라이브러리  Business.Library 는 거의 전부가 참조한다 — 건드리면 그 자체가 한 건이다
```

**기존 구조를 따른다.** 파일이 크다고 임의로 쪼개지 않는다. 다만 고치려는 파일이
이미 감당 안 되게 커졌으면 쪼개는 것을 설계에 넣는 것은 괜찮다.

## 작업 단위

**한 작업 = 따로 확인할 수 있는 것 하나.**

설정·준비·문서 같은 곁가지는 **그것이 필요한 작업 안에 넣는다.** 따로 빼지 않는다.
나누는 기준은 하나다 — **리뷰하는 사람이 이건 통과, 저건 반려라고 가를 수 있나.**

각 작업은 **그 자체로 확인 가능한 결과물**로 끝난다.

## 빈말

아래는 전부 **설계 실패**다. 적혀 있으면 설계가 덜 된 것이다.

```
TBD · 추후 · 나중에 · 상세는 구현 시
「적절히 예외 처리」 · 「필요시 검증 추가」 · 「엣지 케이스 처리」
「Task 3 과 비슷하게」          읽는 사람은 순서대로 안 읽는다. 다시 적어라
무엇을 할지만 적고 어떻게는 없는 단계
어디에도 정의되지 않은 메서드·테이블·설정을 쓰는 단계
```

**「적절히」가 나오면 그 자리가 아직 안 정해진 것이다.** 모르면
`<!-- UNWRITTEN -->` 을 적고 **누구에게 물어야 하는지**를 남긴다.
빈말로 덮는 것과 모른다고 적는 것은 다르다.

## 반드시 들어가는 것

```
파일 경로      정확하게. C:\{형상관리루트}\... 까지
바뀌는 내용     코드가 바뀌면 코드를 보인다. 설명만 적지 않는다
확인 방법      명령과 기대 결과. dotnet build 종료코드 0 · 화면에서 무엇이 보이나
영향범위       이 작업이 어느 기술기반에 걸리나
```

## 자체 검토

**서브에이전트를 부르지 않는다.** 직접 훑는 체크리스트다.

```
1  요구 대비 빠진 것          01-requirements 의 항목마다 대응하는 작업이 있나
2  빈말 훑기                 위 목록의 표현이 하나라도 남아 있나
3  이름이 일치하나            앞에서 정한 메서드·컬럼 이름을 뒤에서 다르게 쓰지 않았나
```

3번이 특히 잘 샌다. 앞에서 `GetResult` 라 해 놓고 뒤에서 `GetResults` 라 쓰면
그대로 버그가 된다.

찾으면 그 자리에서 고친다. **요구에 대응하는 작업이 없으면 작업을 더한다.**

## 설계가 끝나면

`03-design-{제목}.md` 에 쓰고 **승인을 받는다.** 승인 전에 코드를 만지지 않는다.

영향범위 밖의 파일이 설계에 들어 있으면 그 사실을 **4절에 적는다.**
조용히 넓히지 않는다.
